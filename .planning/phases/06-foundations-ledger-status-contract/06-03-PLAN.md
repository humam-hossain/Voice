  <name>Task 1: Serialize read-decide-spawn under flock</name>
  <files>voice.py</files>
  <action>
Rewrite `toggle_background_recording(args)` so the entire read-decide-spawn sequence runs inside `with voicemode_telemetry.with_pid_lock():` (lock file `$XDG_RUNTIME_DIR/voice-stt/.toggle.lock`, created 0600, `LOCK_EX`). Inside the lock, keep the current decision tree, in this order:

1. `pid, state = read_pid_state()`.
2. If `pid and process_alive(pid)` and `state == "starting"`: wait up to 300 ms (20 ms steps) for the child to transition, re-reading state each step; break early when the pid disappears or the state changes (this is the existing D-11 double-tap mitigation — preserve its timing).
3. If a live pid remains: `transcribing` → error cue + the existing "currently transcribing" message + `return 0`; `recording` → `os.kill(pid, SIGUSR1)` + "Stopping voice recording..." + `return 0`; any other live state (`starting`, `typing`, `speaking`, unknown) → print a one-line diagnostic naming the state and `return 0` WITHOUT spawning. This closes the "unknown alive state falls through and spawns a second worker" hole without adding new state strings.
4. If the pid is stale or absent: `remove_pid(pid)` when `pid` was parsed, then `stop_tts(args, quiet=True)`, append the existing log header, `subprocess.Popen(background_argv(args), ... start_new_session=True)`, close the log, `write_pid_state(proc.pid, "starting")`, print the existing start message, `return 0`.

Do all of the above while holding the lock so two concurrent toggles cannot both reach step 4; the loser observes the winner's `starting` PID. Keep the function's exit codes and printed text identical apart from the new unknown-state diagnostic. Do not hold the lock across the 300 ms wait longer than necessary — the wait is inside the lock by design (that is what makes the second press see the first press's worker); cap total hold time at ~1 s by keeping the loop deadline at 0.300 s.

`--cancel` must also take the lock around kill+remove so it cannot interleave with a spawn: wrap the body of `cancel_recording` in `with voicemode_telemetry.with_pid_lock():`.

Lock re-entrancy: `fcntl.flock` is per open-file-description, so a second `with_pid_lock()` in the same process on a fresh fd DEADLOCKS against the first. Do not call `toggle_background_recording`, `cancel_recording`, or any future lock-taking helper from inside the lock. (Verified at planning time: `stop_tts` does not call `cancel_recording`; `cancel_active_stt` is only reached from `speak_selection`, never from the toggle.) Plan 06-06's `reconcile_abandoned_run` is called *inside* the toggle lock and must therefore never acquire it itself.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| toggle invocation → state dir | concurrent processes race on read-decide-spawn |
| worker → PID file | worker asserts and re-asserts ownership of the singleton lock |
| any reader → PID file | readers must tolerate torn/absent content |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-08 | Tampering | `toggle_background_recording` read-decide-spawn | high | mitigate | Entire sequence inside `fcntl.flock(LOCK_EX)` on `$XDG_RUNTIME_DIR/voice-stt/.toggle.lock`; only one process can spawn; verified by a two-thread test asserting a single `Popen` |
| T-06-09 | Spoofing | worker identity | high | mitigate | Worker re-reads the PID file before recording and exits when a *different live* pid owns it; absent/stale file is repairable by claiming it |

| T-06-11 | Tampering | PID file content | low | mitigate | Writers use atomic `mkstemp`+`os.replace` 0600; readers tolerate truncated tokens and return `(None,"idle")` on garbage |
